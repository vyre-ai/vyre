Vyre 0.6.1 is a polish release. It gives a new person a calmer first run, lets agents keep many conversations, and brings plugins and skills into the AI tools you already use.

## What's new

### First run

- A new welcome: a full-screen start, your name, a username and a password, then a name and a look for your Assistant.
- Connect your AI. Add as many accounts as you like, or an API key; the key is typed once and its prefix says which provider it is. The model step lists each account's own models.
- Adding another Space no longer repeats the identity, recovery key or AI steps. The Assistant comes along, and you can copy your AI accounts to the new Space after one confirmation per key.
- A team member's own AI key goes into their own Vault, not the owner's, and the app asks for their password only when it has to.
- The install command for a new Space shows by itself under its name, with a Linux and macOS switch.

### Agents and chats

- A chat is one person and one agent, and an agent can have many. Your threads with an agent are listed newest first with whether each is live, needs you or is idle.
- Every project has one group chat, and you can add people to a chat of several people.
- The Engineer is one chat for everyone in the Space who may use it.
- A forked thread shows "Earlier in the original", and the message menu offers Copy, Rewind, Second opinion and Fork.
- An agent can have a fallback model for when a launch carries on under an API-key account.
- A Flow made from a chat remembers that chat.

### Skills and plugins

- Upload a skill: a SKILL.md, a .md or a .zip of a skill folder or a plugin becomes a draft you approve.
- An approved plugin's MCP servers now reach each AI that supports them: Claude and Grok through a .mcp.json file, and Codex through its config.

### Records and Documents

- Records has People, Companies, Tasks and Notes, a Gallery view, and templates (Blank, Order, Property, Deal) when you add a type. A type has Access and History tabs.
- The first Records list opens faster.
- A role that has Documents on can download a signed request's audit file into its own Files.
- Documents opens faster, because its two Word libraries load on first use.

### Files and Vault

- Move, rename and delete files and folders in your Space's Drive.
- Refusals in Files, the audit file, the key check and the Vault member link now say what to do next.

## Fixed

- A computer that comes back in contact while its sessions are still stopping after a lease end keeps its workspace open. A workspace is never reported locked while it can still be read.
- An app whose start fails after its front began listening no longer leaves a port open with nothing to stop it.
- A new Space that cannot start from its saved database says so.
- Approving a drafted item that waits for a check (Approve or Send in the app) was refused by a real server. It now works.

## Security

Security: in 0.6.0 the per-agent Linux user split on the Space computer never started: the service that makes those users (agentd) could not start inside the computer, and the failure was not reported. Agents on a box therefore used one shared browser, with a separate browser context for each agent, and not a user of their own. We know of no way one agent could read another agent's data in that mode, but it was weaker than the 0.6.0 notes said. 0.6.1 turns the shared browser off by default: each agent gets its own computer again, as before 0.6, and agents share nothing. The shared browser and the per-agent users on one computer come back in 0.6.2, with a proof that runs in a real container. A setting named computers.browse = "browser" still turns the shared browser on by hand. Known issue: a file that an agent's browser downloads may not appear in the agent's Downloads folder; this is fixed in 0.6.2.

## Known gaps

- The shared browser and the per-agent users on the Space computer are off until 0.6.2.
- A file an agent's browser downloads may not appear in the agent's Downloads folder yet; this is fixed in 0.6.2.
- A check given to a role (for example role:reviewer), not to a person, finds no one on a real server. In a Flow the step fails. In a Playbook the to-do is not created and the stage can move on without that check; a stage.error is recorded. Name a person for the check until 0.6.2, which fixes both.
