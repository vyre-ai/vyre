# ADR 0024 · Chat: new sessions, the box's folders, a terminal in the browser, and questions

Status: proposed, 27 Sep 2026 · Workstream: chat · Spec: section 7.8 (the switchboard), Chat

## The problem

On the Deck, the user could read and answer sessions but could not start one, could not see the
box's folders, and had no terminal. A session read like a chat log, not like Claude Code: tool
calls were one-line chips, and every reply was labelled "claude". Claude Code's own questions
(AskUserQuestion) never reached the Deck as questions. They came as a permission ask for a tool
called AskUserQuestion, which the user could only allow or deny. A permission ask showed a
200-character summary, not what would run.

## Decision

**Events stay small; the transcript is the rich record.** Tool inputs and outputs, thinking and
diffs are never written to the event log (spec 6). The session view reads Claude Code's
transcript through `recall.transcript`, one structured block per line: user, text, thinking,
tool (input and output, redacted and capped), and a turn footer with time and tokens.
`transcripts/` is still the only code that reads the format. Live `thread.*` events draw a turn
as it streams; when the turn ends, the view reads the transcript from where it left off and
replaces the live rows in place. The same read works for terminal sessions the switchboard never
ran, so the Deck mirrors the terminal whoever started the session. `recall.transcript` answers a
person's surfaces only: tool output holds whatever the session read.

**Questions are asks with a kind.** A `can_use_tool` request for AskUserQuestion becomes an ask
of kind `question`, carrying its questions (options, multi-select, previews). The answer goes
back as the Agent SDK does it: allow, with `updatedInput.answers` keyed by question. Every other
ask is kind `permission` and carries `detail` (the whole command, the edit's old and new text,
the URL), redacted and capped, in the asks table only, never in the event. When Claude Code
offers permission suggestions, the ask offers "Always for this", which allows with
`updatedPermissions`. Answers stay on the floor's human-only list, with a presence proof whose
summary names the answer.

**A terminal is a pty, not a session.** `core/term` runs the user's login shell under `script`
(util-linux on the box, BSD on a Mac), so there's no native dependency. Output goes over a
ticketed WebSocket (`/v1/streams/term/pty`, as Glass does) and is never written to the event log
or vyred's log. The first terminal a surface opens needs a passkey (`term.unlock`, a presence
tool). The grant lasts 12 hours for that caller, tailnet node and surface, and a restart forgets
it. A terminal ends 10 seconds after its last viewer leaves, unless a viewer comes back. Guests,
agents and models can't reach any term tool. The folder must pass the files guard.

**Folders come from the files guard.** `files.dirs` and `files.recent` list the box's folders
through `core/files/safety.js`, so the folder browser can never show the vault, Vyre's home, a
dot folder or anything outside the roots.

**Names.** In Chat, the model's replies read "Vyre", or the agent's name in an agent's thread.
The user's own messages read "you".

## Consequences

- A live session that Recall has not indexed yet is read straight from its transcript file.
- The Deck's rich view depends on Claude Code's transcript format. It degrades to the old
  event-only view when `recall.transcript` is missing or fails.
- The tailnet listener must pass WebSocket upgrades through for the terminal to work from a Deck
  at the box's address. Until it does, the terminal works only through vyred's socket (see
  docs/work/chat.md, Needs from others).
